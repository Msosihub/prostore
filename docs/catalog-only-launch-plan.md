# Catalog-only operational relaunch — not production activation

Current direction: see [production release path](production-release-path.md). The owner confirms live providers work; sandbox setup is optional, not a mandatory launch prerequisite. Earlier validation limits remain factual.

## Latest owner clarification

The owner confirmed all past transactions were trials, not customer records. Per-order historical reconciliation is no longer a launch gate for these records. Preserve the old database; carry only suppliers/products and dependencies forward. See [trial supplier/catalog transfer](trial-supplier-catalog-transfer.md) for the current executable preparation path and remaining real evidence requirements. Earlier historical-obligation precautions below describe the conservative original assessment; they do not require reconciling the now-confirmed trial transactions.

## Decision

Prefer a new, fully migrated operational database over an in-place cutoff. Existing code relates orders, ledger credits, supplier balances, returns and chat across shared tables; hiding old orders by date would not isolate wallet balances, stock commitments or late callbacks. A new database can retain the catalog while keeping new financial movements separate. It does not erase historical obligations or make legacy funds available in the new book.

No production database/service/credential change or source export has been executed. The importer is deliberately rehearsal-only; its environment/database guards reject normal application targets. A production importer/cutover requires a separately reviewed action-time plan. No native Prisma17 acceptance is claimed.

## Implemented rehearsal

`lib/catalog-launch.ts` is a pure planner that validates a strict versioned manifest with catalog-only allowlists: brands/categories/subcategories, products, pricing tiers, variants and reviewed source-to-target seller mappings. Unknown fields (including orders, balances or credentials) are rejected. Product IDs, slugs, images, descriptions and dependency IDs remain unchanged. Target seller IDs may differ only through an explicit one-to-one mapping; mapped accounts must already be verified suppliers with verified phones. No users/auth tokens/passwords, private seller documents or historical financial records are imported. Target account setup and public shop-profile preservation remain separate reviewed steps; this tool does not silently manufacture accounts or copy login secrets.

Opening product/variant stock is explicitly supplied and confirmed after reviewing legacy commitments; source stock is not guessed or blindly reused. Reserved stock for old orders and unresolved returns must be excluded or separately controlled. Existing reviews/ratings are not copied without their underlying evidence: imported product rating/count start at zero in the new book, never invented. The source catalog/history remains intact. Completeness attestation must be backed by an approved export inventory, not merely checked to pass validation.

Execution lives only in `tests/integration/catalog-launch.cjs`, using the existing loopback-only fixture client, with matching datasource checks before loading that client. It does not import the application database client. All writes are one transaction, with locked catalog/account/financial tables. Existing orders/history/catalog/nonzero balances refuse the import without changes. Concurrent or repeated imports cannot duplicate catalog rows; the second attempt refuses rather than overwriting. Manifest digest records the exact reviewed input. Only established disposable loopback test targets are accepted; no source connection is opened. No payment, SMS or network provider call is made.

Optional `NEXT_PUBLIC_CATALOG_RELAUNCH=true` displays a new-book notice explaining that older orders/returns/balances remain separate and obligations are not cancelled. It defaults off and was not enabled in any live environment. It is a disclosure, not an isolation mechanism; never activate it without actual approved separate-book routing.

See [relaunch evidence workflow](relaunch-evidence-workflow.md) for the offline catalog/account/stock verifier, unmatched callback queue and remaining provider routing gate.

## Launch gates and sequence

1. Preserve legacy database, migration history, ledger, orders, accounts and evidence. Verify an authorized backup/restore and retain controlled operator/customer-service access. Do not make old financial history publicly readable or discard unresolved cases. Determine who owns legacy returns, payouts and customer support. No obligations are waived.
2. Approve isolated new database and access configuration. Apply the full reviewed migration chain only to that empty target, verify native runtime/build/flows, backups, worker readiness, timeouts, observability and service capacity. No paid upgrade or new credentials are created by the source implementation.
3. Produce a catalog-only export through approved access. Reconcile product count/IDs/slugs/media/tier/variant/dependency inventories; preserve public shop identities and URLs through reviewed mappings. Set up necessary seller accounts through verified onboarding or an explicitly approved identity migration, with least privilege. Do not transfer buyer histories/sessions/passwords by default. Confirm seller approval and transactional consent rather than synthesizing evidence.
4. Review opening stock with sellers against outstanding legacy order allocations, dispatched goods and open returns. Define how later legacy returns affect either inventory book before launch. Do not assign an invented monetary opening balance; new-book zero balances exclude, rather than extinguish, prior amounts. Reconcile each book independently.
5. Native/provider acceptance must verify exact provider-reference binding. New orders get new UUIDs and new attempt references; no old Order/PaymentAttempt IDs are imported. The new webhook rejects unknown legacy references without creating payments or credits; the follow-up evidence workflow retains minimal authenticated unmatched notices for admin review without acknowledging them as processed. This refusal alone is NOT legacy callback handling: arrange an approved provider callback dispatcher/endpoint separation with authoritative reference ownership so late legacy events stay in legacy review. Never acknowledge/discard or replay them as new orders. Existing disputed/undelivered obligations remain served privately.
6. Stage catalog import, test browse/cart/order/payment/delivery/dispute and seller/admin isolation with mocks; separately verify provider-approved nonchargeable acceptance. Compare source and target catalogs before cutover and freeze/coordinate catalog edits only during an approved window. Keep financial execution policy gates.
7. Approve exact code/database/domain/worker configuration and activate new-book notice. Route new order creation consistently to the new book. Record cutover boundary and inspect health; no production activation is authorized by this document.

## Rollback after new orders exist

Never point the application back to the old database and lose visibility of new orders. Preserve the new database, references and queued events. Roll back application code only to a version compatible with the new schema/book, or pause new acceptance through an approved maintenance action while continuing existing obligations. Route callbacks by recorded reference ownership to the correct book during rollback; prevent duplicate acceptance across books. Catalog rollback must preserve any new stock deductions/edits. Restore a backup only through a reconciled recovery procedure that accounts for post-backup orders/payments; never blindly restore over them. Test this plan with representative synthetic post-cutover orders before activation.

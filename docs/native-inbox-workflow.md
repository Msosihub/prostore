# Native inbox workflow and remaining integration boundaries

Buyer/seller chat uses the native product-scoped inboxes and canonical-priced proposals. This tranche adds server-side product-name search across owned threads, and a live view of the 30 most recent unread threads. Normal/search history remains cursor-paginated; unread is explicitly bounded. Reading a selected thread clears its incoming unread state. The UI does not claim SMS, push, delivery acknowledgement, negotiated prices, attachments or working calls.

Polling stops while hidden, does not start overlapping refreshes, and discards responses for superseded filters/threads. Existing interrupted-send idempotency, participant checks, contact validation and proposal/order invariants remain authoritative.

The unused Prostore Chatwoot webhook receiver and SSE relay now return explicit 410 LEGACY_CHAT_RETIRED without reading payloads, emitting events, opening streams or acknowledging processing. Legacy history and its participant-scoped reads remain. Authenticated legacy inquiry/mark-seen compatibility endpoints still exist; they do not invoke Chatwoot or create native messages/proposals. Old quote route files are not active Next route handlers. The broken supplier inquiries navigation now leads to native proposals/messages.

External NestJS writes and Chatwoot webhooks/services are outside this code release and remain unchanged. Their retirement requires checking actual consumers/backups and coordinating ingress shutdown. The separate deferred bot endpoint remains outside this transition. No production service or data was stopped/deleted.

Contact policy applies to newly written native message text and proposals; it is not perfect contextual anti-circumvention and does not retrospectively rewrite history. Split-message contact obfuscation, reporting/blocking, stronger abuse rate limits and paginated proposal history remain follow-up work. Native proposals currently use canonical catalog tiers, not seller-negotiated discounts. Installing another chat platform would not resolve these application authorization/policy boundaries.

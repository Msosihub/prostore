# Product proposals and order/payment cards

Product discussion stays bound to one buyer, seller and canonical product. The labelled product card links back to that product; a different product opens its own product conversation in the same inbox. Free text is not a product tag, price override or payment instruction. Existing contact controls and participant boundaries remain.

Sellers may choose no deadline (backward-compatible default), 1 hour, 24 hours, 3 days or 7 days when creating a proposal. The server sets the immutable deadline from the creation time. Exact request retries preserve that deadline; reusing the same request ID with different duration fails. Existing proposals remain non-expiring. A new proposal is required to replace an expired one. No inventory reservation or price guarantee is implied: canonical catalog/tier price, stock, ownership and buyer address are checked again at acceptance. Negotiated prices are not implemented; no discount authority or pricing policy was invented.

Both participants see the deadline in East Africa Time. Expired proposals remain in history with a clear state and no accept link. Expiry is enforced server-side during review and again after supplier lock waits before order creation. Client clock/render timing is only a display hint; server checks decide. The review fingerprint binds deadline, quote and address. Accepting an already accepted proposal returns its original order even after the deadline; it never creates another order or payment. Proposal status remains OPEN in storage after expiry; expiry is derived, requiring no scheduled mutation. Accepted orders and cancellation retain their existing semantics.

Accepted proposals display an order reference and minimal authoritative payment state. Pending with a durable payment attempt means awaiting confirmation; a newly created PENDING order without an attempt is not claimed to be awaiting a charge; review-required warns against paying again; paid is shown only from Order.isPaid. This is a system status card, not a seller-issued payment receipt/voucher. No customer address, phone, provider payload, secrets or other seller allocations are exposed in the card. Only the buyer receives the existing authorized order/checkout link. Opening chat or accepting a proposal never charges; explicit buyer checkout remains separate. Payment is not delivery confirmation. No new arbitrary payment links, Selcom adapter, notification or provider call was added. ZenoPay's existing initiation/status/settlement flow remains unchanged; the supplied guide is not evidence of Selcom compatibility or new-code live acceptance.

## Deployment and verification

Additive migration `20261031030000_market_proposal_expiry` adds a nullable timestamp to MarketProposal without rewriting history. Apply only with the complete reviewed migration sequence to an approved target. Production remains unchanged. Existing source packaging/credential, hosting, worker, native Prisma and provider verification gates remain; no new download attempt or alternate route around the known native engine403 was used.

Isolated validation results are recorded in the PR and handoff. PostgreSQL tests cover role/participant isolation, allowed/invalid duration, concurrent idempotent creation and acceptance, expiration after review and supplier lock waits, unchanged legacy proposals, fingerprint consent, and the exact minimal payment DTO. Browser checks cover product context, seller duration, buyer review/order link, pending then verified mocked payment state, seller read-only card and expired-proposal UI. Mocked payment acceptance is not provider acceptance. No real messages or financial operations.

Browser regression also exposed a pre-hydration staff form submit. The review button now stays disabled until its client handler is ready; browser checks require the actual POST response and persisted audit event, not just a click. This preserves the existing authorized review action and creates no new moderation capability.

Full optimized fixture build including TypeScript checking against its generated test client and browser scenarios `flow,cart,payment,delivery,chat,market-chat` passed. Mobile proposal/payment/staff-review screenshots were inspected. The initial browser run found the fresh-PENDING payment label defect; the next exposed the staff form readiness issue; both were corrected and the complete selected workflows passed on rerun. Independent read-only review found no remaining concrete blocker. These use the established test-only JavaScript Prisma adapter/font/provider fixtures; native deployment runtime was not verified and the denied engine download was not retried.

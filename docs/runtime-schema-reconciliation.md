# Guarded forward runtime reconciliation

`20261027020000_runtime_marketplace_baseline` repairs omitted Prostore schema DDL without editing historical migrations. It adds SupplierLedger, OrderItemEvent, OrderDeliveryFeedback and ReturnRequest, their exact existing Prisma types/defaults/primary keys/unique indexes, two status enums, nine User/OrderItem columns and eight legacy Prostore Message/Conversation columns. It also aligns four timestamp precisions and the Inquiry product UUID/foreign-key contract. Any timestamp conversion that would discard microseconds or invalid/orphan product reference is refused before writes. No financial or delivery policy is changed. The four table models have no Prisma relations, so this migration does not invent foreign keys.

## What can safely apply

A fresh database following the historical chain can apply the repair. Existing nonfinancial users/suppliers and empty conversations can remain. The migration runs inside an explicit transaction with a five-second lock timeout and exclusive source-table locks; concurrent source writes cannot slip between inspection and DDL.

It refuses any existing order items, paid/delivered/nonpending orders, nonzero supplier balances, payout requests, durable payment attempts, money-review cases, notification records or legacy messages. Their missing fulfillment, ledger or update-time facts cannot be reconstructed from guesses. It also refuses undeclared/partial runtime tables, enums or columns instead of silently accepting incompatible objects. Failure leaves existing schema/data unchanged. Do not reset a database or delete records to satisfy these guards.

For a refusal, use an authorized staging clone and the read-only preflight queries. Compare schema plus `_prisma_migrations` names/checksums/completion metadata, then prepare a separately reviewed adoption/reconciliation migration using authoritative source records. Do not mark this migration applied merely because some tables exist. Prisma failed-migration resolution also requires confirming rollback and a reviewed operator plan; no such operation was run here.

## Verification and limits

`npm run test:migrations:isolated` creates its own network-disabled PostgreSQL16 container with no published ports, replays all SQL and removes the container. It compares all Prostore-owned runtime table/column/nullability, scalar types/precision and enum presence; detailed repaired-object checks additionally cover exact column types/precision/defaults, PK/FK expectations, unique indexes and ordered enum labels. Populated refusal cases compare before/after schema and row fingerprints. A concurrent financial writer verifies lock/guard ordering. Wrong-column and partial unique indexes are rejected by preflight, rather than trusted by name. The actual migrated schema is dumped/restored into another disposable database, including a synthetic ledger row.

The remaining imported lowercase Chatwoot models are not provisioned here. They are a separate integration schema, not the first-party marketplace table set. Their exact missing objects remain enumerated by the audit rather than being silently reported as matching. This does not repair or activate the deferred external integration.

Native Prisma engine binaries remain unavailable in the inspected installed/cache locations. No prior denied download route was retried. SQL replay and fixture-adapter application tests are not `prisma migrate deploy`, native runtime or hosting proof.

## Workers: approval and staged validation, not automatic activation

Existing trusted services are `notificationBatch({dryRun:true, limit:20})` and `reconciliationBatch({dryRun:true, limit:20})`. Neither has a scheduler enabled. First validate read-only candidate selection against authorized staging; then mock execution and crash/lease/duplicate recovery; then obtain provider sandbox acceptance before configuring any real worker. Limit each batch (maximum50), prevent overlapping unbounded runners, and monitor backlog/oldest age, expired leases, UNKNOWN/FAILED and payment review states. `scripts/worker-health-preflight.sql` reports only aggregate queue evidence without recipients, bodies or credentials. Acceptance is not delivery; absence of a backlog does not prove worker health. Preserve UNKNOWN manual review rather than blind retries. Alerting thresholds/cadence and the owning operator must be explicitly chosen for actual traffic before activation.

## Practical release options

1. **Full stack:** still requires staging baseline reconciliation for any populated environment, native runtime/build/migration proof, provider acceptance, approved workers, tested rollback/backup, policy decisions and hosting access. Financial execution remains disabled. Do not deploy the draft stack on fixture evidence alone.
2. **Smaller storefront-only backport:** possible source scope is homepage/product cards/header/category navigation/crawlable pagination and truthful metadata/sitemaps, based on the actual deployed commit. PR12 is not directly independent: its root layout queries MarketMessage; product UI references StartProductChat; footer links target newer refund/chat pages; search uses catalog-search. A backport must retain existing chat/counting/checkout links, add only required catalog presentation helpers and avoid auth/payment/order/worker/migration changes. Independently test the resulting branch against a sanitized staging schema with native runtime and existing purchase workflows. No such candidate has yet been built or approved.

For either option, identify the actual deployed SHA and verify hosting project, environment scope, current deployment and rollback target through authorized access. Parent reports the connected Vercel account exposes zero teams and prior project access was denied; those reads were not retried or bypassed. The smallest access prerequisite is an authorized connection to the owning hosting team/project. Credentials/security configuration are not changed by this work. A storefront backport would not resolve pre-existing checkout security defects and must not be presented as full-platform readiness.

Tests cover referenced refusal, unreferenced success and concurrent order creation/deletion. No foreign-key policy or historical migration was changed to hide the failure.
